# 가독성 판단과 리뷰

판단 질문: 실제로 읽는 비용이 있는 코드입니까, 내게 낯선 코드입니까.

## 쓴 직후 점검

코드를 쓴 쪽은 맥락을 다 알고 있어서 자기 코드가 쉬워 보입니다. diff 를 처음 보는 사람 입장에서 다시 읽습니다.

- 함수 이름과 시그니처만 보고 동작을 말할 수 있습니까
- 이번에 새로 만든 함수, 타입, 파일이 각각 같이 기억할 항목을 줄입니까. 줄이지 않으면 없앱니다.
- 근처 코드와 모양이 같습니까

## 읽기 어렵다고 지적할 때

「읽기 어렵다」로 끝내지 않고 비용을 적습니다.

- 어느 줄에서 무엇을 같이 기억해야 합니까
- 어느 이름이 실제 동작과 다릅니까
- 어느 패턴이 코드베이스의 어느 코드와 다릅니까
- 어떻게 바꾸면 그 비용이 사라집니까

## 낯선 것과 어려운 것 구분

지적하기 전에 확인합니다.

- 언어의 표준 관용구이면 지적하지 않습니다.
- 같은 레포에서 이미 쓰는 패턴이면 지적하지 않습니다.
- `for` 와 `map` (example) 처럼 취향이 갈리는 선택은 코드베이스 컨벤션이 정해져 있을 때만 지적합니다.

같은 지적이 반복되면 린터나 컨벤션 문서로 옮기도록 제안합니다.

## 가독성과 정확성은 다른 축

- 읽기 쉬운 코드도 틀릴 수 있습니다. 깔끔해 보여도 로직 검증을 생략하지 않습니다.
- 리뷰 결과에서 동작 결함과 가독성 지적을 구분해서 씁니다.

## 지표

- 줄 수, 함수 길이, cyclomatic complexity(분기 경로 수) 는 참고 신호로만 씁니다.
- 지표가 좋아졌다는 것만으로 읽기 쉬워졌다고 말하지 않습니다. 지표는 코드의 겉모양을 재고, 읽는 비용은 패턴의 익숙함과 이름에 따라서도 달라집니다.

## 가독성 리팩터링

- 동작 변경과 한 커밋에 섞지 않습니다.
- 전후로 같은 테스트를 돌려 동작이 같은지 확인합니다. 테스트가 없으면 그 사실을 보고합니다.
- 요청 범위 밖의 코드는 고치지 않고 제안만 합니다.
