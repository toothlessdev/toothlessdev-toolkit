# 읽기 쉬운 코드: 판단 기준과 우선순위

코드를 읽기 어렵게 만드는 비용은 다섯 가지입니다. 코드를 쓰거나 고칠 때 각 파일의 규칙으로 이 비용을 줄입니다.

| 비용 | 언제 생깁니까 | 규칙 파일 |
| --- | --- | --- |
| 같이 기억할 항목이 많습니다 | 한 줄을 이해하려고 바깥 조건과 변수를 계속 떠올려야 합니다 | `01-function-boundaries.md`, `02-control-flow.md` |
| 처음 보는 모양입니다 | 아는 패턴이 아니라서 요소를 하나씩 따져 읽어야 합니다 | `03-conventions.md`, `02-control-flow.md` |
| 구조가 보이지 않습니다 | 줄 배치만 봐서는 어디까지가 한 덩어리인지 알 수 없습니다 | `04-code-layout.md` |
| 예상과 다릅니다 | 이름과 시그니처를 보고 한 예상이 실제 동작과 어긋납니다 | `05-predictability.md` |
| 표현이 문제보다 복잡합니다 | 문제에 없는 계층, 옵션, 상태가 코드에 있습니다 | `06-accidental-complexity.md` |

가독성을 판단하거나 리뷰할 때는 `07-review.md` 를 따릅니다.

## `(example)` 표시

`(example)` 이 붙은 코드와 식별자는 규칙의 뜻을 보여주는 설명입니다. 따라 쓸 모범 답안이 아닙니다.

- 판단은 규칙 문장과 판단 질문으로 합니다. 예시와 닮았는지로 판단하지 않습니다.
- 예시의 이름, 도메인, 클래스 구조, 라이브러리 사용법을 새 코드에 옮기지 않습니다.
- 예시와 모양이 달라도 규칙을 어겼으면 고치고, 모양이 닮아도 읽는 비용이 없으면 고치지 않습니다.
- 규칙 문장에 나온 구체적인 이름은 전체 목록이 아닙니다. 같은 뜻의 다른 이름에도 똑같이 적용합니다.
- 예시는 Kotlin 과 Spring 으로 썼지만 규칙은 언어와 프레임워크와 상관없이 적용합니다. 언어마다 다른 관용구와 구조는 그 언어와 코드베이스 쪽을 따릅니다.

## 규칙이 부딪힐 때

위에 있는 항목이 우선합니다.

1. **동작이 맞는 코드**: 읽기 쉽게 고치다가 동작을 바꾸지 않습니다.
2. **사용자의 지시와 프로젝트 문서**: 사용자나 프로젝트 문서(`CLAUDE.md` 등)가 정한 방식이 이 규칙과 달라도 그 방식을 따릅니다.
3. **고치는 파일과 모듈의 기존 패턴**: 더 나은 형태가 떠올라도 요청 범위 밖이면 기존 패턴을 따릅니다.

## 규칙에 나오는 숫자

- 숫자는 다시 보라는 신호이고 합격선이 아닙니다.
- 사람이 동시에 기억하는 양은 과제와 숙련도에 따라 달라집니다.
- 숫자를 맞추려고 코드를 쪼개지 않습니다.
