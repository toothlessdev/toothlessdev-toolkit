# Decision Table

**분류** specification-based · **Coverage Item** 각 rule

## 언제

불리언 조건 여러 개의 **조합**으로 결과가 결정될 때. 조건을 하나씩 따로 테스트하면 조합 효과를 놓칩니다.

## 규칙

1. 명세에서 **조건(condition)** 과 **결과(action)** 를 뽑습니다.
2. 조건 조합마다 rule 을 만듭니다. 조건이 n 개면 최대 2^n.
3. **불가능한 조합을 제거합니다.** 명세가 배타 관계를 말하면 그 조합은 rule 이 아닙니다.
4. 남은 rule 하나가 Coverage Item 하나.

조건 `C1`, `C2` 와 결과 `A` 에 대해:

| rule | C1 | C2 | → A |
|---|---|---|---|
| R1 | T | T | `a1` |
| R2 | T | F | `a2` |
| R3 | F | T | `a3` |
| R4 | F | F | `a4` |

`a1`~`a4` 는 **명세가 각 조합에 지정한 결과**입니다. 명세를 보기 전에 미리 채워두지 마세요.

## 압축은 하되 기록을 남겨라

같은 결과를 내는 rule 을 `-`(don't care)로 합치면 케이스 수가 줍니다. 합쳤으면 `rationale` 에 어느 rule 들을 합쳤는지 적습니다.

```
a1 = a2 = a3 이면   →   C1 ∨ C2 → a1
```

**단, 합치기 전에 명세를 다시 읽으세요.** 결과가 같아 보여도 **명세가 서로 다른 근거로 같은 결과를 지정한 것이라면 별개 rule 로 둡니다.**

## 결과가 명세에 없는 조합

조합은 만들어졌는데 명세가 그 경우의 결과를 말하지 않으면 **기대값을 추측하지 마세요.** `ambiguities` 에 `Ambiguity` 항목을 올리고, 해당 커버리지 항목 id 를 `blockedCoverageItems` 에 적습니다.

"당연히 이렇게 되겠지"는 근거가 아닙니다. 실무 결함의 상당수가 그 "당연히" 에서 나옵니다.

## 도출 흐름

<example>
명세가 조건 `C1`, `C2` 로 결과를 결정할 때.

```
Test Condition
  statement    <C1 과 C2>의 조합에 따른 결과 결정
  basisRefs    두 조건을 정의한 명세 항목 전부

Coverage Item  rule 하나당 하나
  R1   C1 ∧ C2                → 명세가 지정한 결과
  R2   C1 ∧ ¬C2               → 명세가 지정한 결과
  R3   ¬C1 ∧ C2               → 명세가 지정한 결과
  R4   ¬C1 ∧ ¬C2              → 명세가 지정한 결과

Test Case
  inputs       각 rule 의 조건을 참/거짓으로 만드는 파라미터 값
  expected     그 rule 에 명세가 지정한 결과
  rationale    어느 rule 인지 + 왜 그 결과인지
```

`description` 의 `C1`, `C2` 자리에는 **명세 문장에서 읽어낸 조건**을 적습니다.
</example>
